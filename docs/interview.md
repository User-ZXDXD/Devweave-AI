# DevWeave AI 面试讲解与演示

## 三分钟讲解顺序

**约30秒，问题。** 这个产品面向研发协作。一个PR是否可以推进，往往要同时看Issue、变更、CI、Review和项目约束。通用问答容易缺上下文，也容易把建议与执行混在一起。

**约60秒，实际流程。** 从产品演示页进入Issue、PR或CI功能，展示输入、结构化分析和证据。再解释多Agent工作流：模型提出计划，程序校验和调度，专用Agent执行，Observer检查，最后综合；不是所有步骤都调用模型。

**约45秒，验证。** 展示本次回归记录与一个失败分支：数据不足时阻止贸然给结论，或模型不可用时明确降级。演示模式没有调用真实LLM，应当直接说明。用测试和输出证据解释实现，不声称已经验证生产提效。

**约45秒，取舍。** 结构化实时状态查数据库/API，当前代码用工作区检索，文档用RAG；合并和发布要人工确认。说明本地演示与完整部署的区别，并提出下一步用真实任务集验证完成率和错误方向。

## 五分钟操作路线

| 顺序 | 打开哪里 | 展示什么 |
| --- | --- | --- |
| 1 | `/showcase` | 当前实际数据量、离线标签、三条任务路径与配置状态 |
| 2 | `/issues` | 示例问题、分析输出、问题分级与行动项；不要把规则输出说成真实模型输出 |
| 3 | `/pull-requests` 或 `/ci` | PR/CI上下文怎样支撑结论，以及有哪些缺口 |
| 4 | `/workflow-runs`、`/action-drafts` | 任务执行记录与人工确认边界；没有新执行时不伪造一条运行记录 |
| 5 | `/evals` 与验证报告 | 指标口径、样本和跳过项；不是只展示一个总分 |

## 能被追问的十二个问题

| 问题 | 回答时要落到哪里 |
| --- | --- |
| 为什么不用一个长Prompt完成所有事？ | 不同任务需要不同来源和输出契约；说明拆分成本、延迟与适用边界 |
| Planner负责什么，程序负责什么？ | `backend/app/services/agents/planner_agent.py` 与 `workflow_orchestrator.py`；语义规划和依赖调度分开 |
| Observer会不会自己也判断错？ | 硬门禁、引用验证与语义检查分别解释；引用存在不证明逻辑正确 |
| 什么情况下应该使用RAG？ | 文档、历史经验与多源知识；当前状态和代码仍回权威来源 |
| 如何避免把别的仓库数据混进来？ | 仓库／会话作用域、检索过滤、评测副本及对应测试；不泛称完全解决所有多租户安全 |
| 模型不可用怎么办？ | `llm`、`rules`、`rules_fallback`标记；降级不伪装为成功语义检查 |
| 为什么默认离线演示？ | 面试复现成本可控；但只能证明本地流程，完整外部链路另验 |
| 为什么生成草稿而不是直接合并？ | 外部写入有后果，分析结果不构成授权；核对现有确认与审计流程 |
| 同时触发同步会怎样？ | PostgreSQL advisory lock与SQLite单进程互斥的差别；不要把演示锁解释成分布式队列 |
| 怎样评价Agent效果？ | 软件契约、固定任务集、证据与人工标注；完成率、误导建议率和成本分别报告 |
| 你这次做了什么？ | 如实区分已有实现、本次AI辅助产品化整理、实际运行验证和个人理解；不要把全部既有功能都说成新写 |
| 下一版先做什么？ | 从失败案例选择一个可验证问题，例如证据不足时的正确拒答；先给最小对照和指标，不先堆功能 |

## 说法边界

可以说“基于现有DevFlow实现完成产品化整理、演示与验证”，并说明具体参与动作。只有亲自完成并能定位证据的部分，才作为自己的独立贡献陈述。不编造用户访谈、生产用户量、提效比例、招聘录用或从零手写经历。
